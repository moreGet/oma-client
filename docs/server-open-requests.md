## 2. 🔴 P0 — LLM 공급자 호출 실패가 반복됩니다

### 관측 사실 (2026-07-30 클라이언트 로그, 실측)

```
13:51:20  [WARN] ContextCompactor  이력 요약 실패 — 생략 폴백으로 진행
          AgentException: 요약 요청 실패: [backend_error] llm provider request failed
13:51:38  같은 실패
13:51:57  같은 실패 (원인 다름 — §3 참조)
13:52:09  같은 실패
13:52:35  같은 실패
13:52:45  같은 실패        → 85초 동안 6회
```

### 무엇이 망가지는가

이 실패는 **대화 이력 요약(컴팩션)** 경로에서 났습니다. 클라이언트는 대화가 길어지면 오래된 구간을 서버에 요약 요청하고, 실패하면 **요약 대신 그냥 잘라내는(생략) 폴백**으로 넘어갑니다. 즉:

- 앱은 죽지 않지만 **대화의 앞부분 정보가 요약본 없이 사라집니다** — 긴 작업에서 에이전트가 앞 맥락을 잊습니다.
- 실패 1회마다 **요청 1건 + 오래된 대화 전문(최소 20,000자, 최대 300KB 규모) 업로드**가 낭비됩니다.
- 같은 조건이 유지되면 **한 턴에 최대 25회까지** 반복 시도합니다(클라 측 반복 상한). 실패가 쿼터와 대역폭을 태웁니다.

### 서버에 요청하는 것

1. **`llm provider request failed` 의 실제 원인 확인** — 공급자 쿼터 초과 / 타임아웃 / 인증 / 리전 장애 중 무엇인지. 서버 로그에 공급자 응답 원문이 남는지 확인해 주세요.
2. **원인별로 `code` 를 나눠 주세요.** 지금은 전부 `backend_error` 로 뭉개져 클라이언트가 "일시 장애" 로만 해석합니다.
   - 공급자 쿼터 초과라면 → **429 + `rate_limited`** (클라가 "사용량 초과" 로 정확히 안내)
   - 공급자 인증 실패라면 → 서버 설정 문제이므로 5xx 유지하되 **운영 알림**이 필요
   - 요청이 공급자 상한(토큰·크기)을 넘었다면 → **400 + `bad_request`** (클라가 재시도로 낭비하지 않게)
3. **요약 요청은 크기가 큽니다**(대화 전문). 공급자 입력 상한에 걸리는 것이 원인이라면 알려 주세요 — 클라이언트 쪽에서 요약 입력을 잘라 보내는 방식으로 대응할 수 있습니다.

> **클라이언트 측 대응도 별도로 진행합니다** — 연속 실패 시 재시도를 멈추고(현재 백오프 없음), 첫 실패 때 사용자에게 1회 알리도록 고칠 예정입니다. 다만 그건 낭비를 줄이는 것이고 **근본 원인은 서버 쪽입니다.**

## 3. 🔴 P0 — SSE 응답이 중간에 끊깁니다

### 관측 사실

```
13:51:57  HttpRequestException: An error occurred while sending the request.
          └ HttpIOException: The response ended prematurely. (ResponseEnded)
```

`POST /api/v1/agent/chat` 의 **SSE 스트림이 완결 이벤트 없이 끊겼습니다.** 클라이언트에는 원인 불명의 연결 오류로 보입니다.

### 서버에 요청하는 것

1. **어디서 끊었는지 확인** — API 앱 / nginx / 공급자 중 누가 먼저 닫았는지. nginx 라면 `proxy_read_timeout`·`proxy_buffering` 설정을 확인해 주세요.
2. **SSE 에는 버퍼링을 걸지 마세요** (`proxy_buffering off`, 압축 제외). 버퍼링이 걸리면 토큰이 모였다 나오거나 이렇게 끊깁니다 — 이건 `server-compression-spec.md` 에 이미 요구로 적혀 있습니다.
3. **에러 상황에서도 SSE 에러 이벤트로 끝내 주세요.** 스트림을 그냥 닫으면 클라이언트가 원인을 구분할 수 없습니다. 정상 종료든 실패든 **명시적 이벤트**로 마무리되어야 합니다.
4. 게이트웨이 타임아웃이 모델 실제 소요보다 짧지 않은지 확인해 주세요.

## 4. 🟡 P1 — 이미지 생성 엔드포인트 (신규)

**상세: [`docs/server-image-api.md`](server-image-api.md)** — 그대로 구현 프롬프트로 쓸 수 있게 작성했습니다(수용 기준 + curl 포함).

- 요구: `POST /api/v1/images/generations` 1개. 요청 `{prompt, size, count, format}` → 응답 `{images:[{b64, revised_prompt}], usage}`
- **클라이언트는 선구현 완료** — 서버가 올라가면 클라 수정 없이 동작합니다.
- 지금은 404 를 받아 "서버에 이미지 생성 엔드포인트가 없습니다 — 관리자에게 문의하세요" 로 실패합니다(사용자에게는 기능이 없는 것과 같음).
- 이미지 모델 키는 **서버만** 보유합니다. 클라이언트에는 모델 키도, 모델 ID 도 없습니다(데이터 주권 원칙).
- **base64 인라인으로 주세요.** URL 방식은 폐쇄망에서 이미지 보관·수명 관리 부담 + 왕복 낭비라 채택하지 않았습니다.

## 5. 🟡 P1 — 요청 본문 gzip 수용

**상세: [`docs/server-compression-spec.md`](server-compression-spec.md)**

- 클라이언트 구현 완료, **기본 꺼짐**(`AppSettings.CompressRequests = false`). 서버가 압축 본문을 못 읽으면 400/415 로 **요청 자체가 실패**하므로 서버 확인 전에는 켤 수 없습니다.
- **효과가 큽니다** — 에이전트는 도구 왕복마다 대화 전문을 다시 보내고, 그 안에 도구가 읽은 소스 원문이 들어 있어 gzip 이 특히 잘 듣습니다. 실측 **76~80% 감소**(200메시지 세션에서 한 턴 3.7MB → 0.8MB).
- **핵심: 이건 nginx 로 해결되지 않습니다.** 요청 본문 해제는 **API 앱**이 해야 합니다(이유는 상세 문서의 "왜 nginx가 아닌가" 절).
- 서버가 지원되면 알려 주세요 — 클라이언트에서 기본값을 켜고 실기 검증하겠습니다.

## 6. 🟡 P2 — 이미지 기능의 정책·쿼터 연동

이미지 엔드포인트(§4)와 함께 필요합니다.

| 항목 | 요구 |
|------|------|
| **도구 정책** | `GET /api/v1/tools/policy` 에서 **`generate_image`** 이름으로 켜고 끌 수 있어야 합니다. `enabled` **허용목록을 운영 중이라면 추가하지 않으면 자동 차단**됩니다 |
| **쿼터** | 이미지 초과는 **429 + `rate_limited`** (5xx 아님). 텍스트 쿼터와 **별도 한도**를 권합니다 — 이미지 몇 장이 하루 대화 예산을 태울 수 있습니다 |
| **`count` 상한** | 서버가 강제해야 합니다. 클라이언트 상한만으로는 방어가 되지 않습니다(클라이언트는 신뢰 경계 밖) |
| **realtime 정책** | `POST /api/v1/tools/authorize` 에 프롬프트가 올라오므로 **내용 기반 차단이 가능**합니다 |

전체 도구 목록(37개, 이름·위험도·노출 범위)은 [`server-tool-policy-api.md`](server-tool-policy-api.md) 의 **도구 인벤토리** 표를 보세요 — 클라이언트 코드에서 직접 추출한 정본입니다.

## 7. 에러 계약 — 전 엔드포인트 공통 요구 (재확인)

여러 항목에서 반복되므로 여기 모읍니다. **이건 새 요구가 아니라 기존 계약의 재확인입니다.**

```json
{ "error": { "code": "unauthorized | rate_limited | backend_error | bad_request", "message": "..." } }
```

| 요구 | 어기면 |
|------|------|
| **판별은 상태코드와 `code` 로만 가능** — 클라이언트는 `message` 원문을 사용자·모델에게 보여주지 않고 상태코드/`code` 기준 한국어 문구를 만들어 씁니다(`UserErrorMessages.ForAgentError`) | 자유 문장에 담은 원인 구분이 **클라이언트에서 사라집니다**. 원인을 나눠야 하면 `code` 를 나눠 주세요 |
| **쿼터 초과 = 429** | 5xx 로 오면 일시 장애로 오해해 사용자가 재시도를 반복합니다 |
| **인증 실패 = 401** | 5xx 로 오면 **헤드리스 호스트가 무한 재시도**에 빠집니다(같은 요구가 `server-service-account-api.md` 에도 있습니다). 클라이언트는 **401 에서만 로그아웃**하고 403/429/404/5xx 는 메시지만 표시합니다 |
| **요청 오류 = 400** | 5xx 로 오면 모델이 일시 장애로 보고 같은 인자로 재시도해 턴을 낭비합니다 |
| 429 의 `message` 에 `daily`/`weekly`/`monthly` 중 하나 포함 | 클라이언트가 기간을 문구에 반영합니다(이것만 예외적으로 `message` 를 봅니다) |

## 8. 우선순위 제안

1. **먼저 §2·§3(안정성)** — 이미 실사용을 방해하고 있습니다. 신규 기능보다 앞섭니다.
2. **다음 §5(요청 gzip)** — 코드 변경이 작고 효과가 즉시 큽니다(전송량 76~80% 감소). 클라이언트는 준비 완료.
3. **그다음 §4·§6(이미지)** — 신규 기능. 클라이언트 선구현이 끝나 서버만 올리면 됩니다.
4. 나머지는 여유 있을 때.
