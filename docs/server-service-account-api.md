# 서버 API 요구 스펙 — 서비스 계정 · 장수 자격증명

대상: 서버(API) 팀(`OhMyAgent.AiAgent.Server`).
작성: 클라이언트(`OhMyAgent.AiAgent.Host` — 헤드리스 에이전트).
우선순위: **High** — 현재 헤드리스는 사람 계정 JWT를 재활용하는 것 외에 방법이 없습니다.

> 관련: 도구 정책 `server-tool-policy-api.md` · 레지스트리/A2A `a2a-registry.md` · 배포 `headless-deployment.md`

---

## 1. 배경 — 지금 무엇이 문제인가

헤드리스 에이전트는 토큰을 `OHMYAGENT_AUTH_TOKEN` 환경 변수로 주입받습니다. 그런데 현재 발급 가능한
자격증명은 `POST /api/v1/auth/login`이 주는 **사람용 JWT뿐**입니다. 이걸 데몬에 넣으면 세 가지가 깨집니다.

| 문제 | 내용 |
|---|---|
| **만료** | 데몬은 24/7 도는데 JWT는 만료됩니다. 헤드리스에는 재로그인 UI가 없어 자가 갱신이 불가능합니다 |
| **권한 과다** | 사람 계정 토큰을 넣으면 에이전트가 **그 사람의 권한을 그대로 상속**합니다. 최소 권한 원칙 위반 |
| **감사 불가** | 서버 로그에서 "사람이 한 일"과 "에이전트가 한 일"이 같은 member로 뭉개집니다 |

클라이언트는 이미 만료를 **감지해 종료**하도록 고쳐 뒀습니다(종료 코드 77 → systemd 재시작). 다만 그건
증상 완화이고, 근본 해결은 **만료되지 않거나 회전 가능한 서비스 계정 자격증명**입니다.

## 2. 요구 사항

### A. 서비스 계정 (필수)

사람과 구분되는 계정 종류가 필요합니다. 최소 요건:

- 비밀번호 로그인 불가(대화형 인증 경로 없음)
- 기존 **도구 정책·쿼터·명령 보안 정책이 그대로 적용**될 것 — 계정 종류만 다르고 정책 평면은 동일해야
  클라이언트가 코드 변경 없이 동작합니다
- 소유자(담당 팀·사람)를 기록해 폐기 책임자를 추적

### B. 장수 API 키 (필수)

| 항목 | 요구 |
|---|---|
| 수명 | 기본 무기한 또는 **90일 이상** 선택 가능 — 2026-07-27부터 **서버가 발급 시점에 강제**(↓ 하한 계약) |
| 형식 | 기존 `Authorization: Bearer <값>` 그대로 — **클라이언트 변경 0** |
| 발급 | 평문은 **발급 응답에서 1회만** 노출. 서버는 해시만 보관 |
| 폐기 | 즉시 무효화(다음 요청부터 401) |
| 회전 | 계정당 **키 2개 이상 동시 유효** — 무중단 회전에 필요 |

> **회전에 키 2개가 필요한 이유**: 헤드리스는 재시작으로만 토큰을 바꿉니다. 새 키 발급 → 유닛 파일
> 갱신 → 재시작 → 구 키 폐기 순서를 밟으려면 그 사이 두 키가 모두 유효해야 무중단이 됩니다.

#### B-1. 키 수명 하한 90일 — 서버 강제 (2026-07-27 반영 완료)

원래 "90일 이상"은 이 문서의 운영 권고일 뿐이라 서버는 미래 시각이기만 하면(예: 1초 뒤) 키를 발급했고,
운영자가 실수로 초단기 키를 발급하면 헤드리스가 조기 401로 죽었습니다. 이제 서버가 발급 시점에 하한을
강제합니다. 서버 구현: `internal/domain/serviceaccount/model.go`의 `MinKeyLifetime = 90 * 24h`.

| 입력 `expires_at` | 결과 |
|---|---|
| 생략 / `0` (무기한) | `201` — 하한 적용 대상 아님 |
| 과거·현재 | `400 expires_at must be in the future` |
| 미래, `now + 90일` 이상 | `201` |
| 미래, 90일 미만 | **`400 expires_at must be at least 90 days in the future`** |

```jsonc
// POST /api/v1/service-accounts/{id}/keys   (admin JWT)
// expires_at 은 RFC3339 가 아니라 unix epoch seconds(int64). 생략/0 = 무기한(0 sentinel 때문의 의도적 이탈)
{ "expires_at": 1801036800 }

// 400 — 하한 위반 (평면 에러 envelope)
{ "code": "BAD_REQUEST", "message": "expires_at must be at least 90 days in the future" }
```

- 경계값 `now + 90일` **정확히는 통과**합니다(`>=` 비교).
- 기준 시각은 **서버의 발급 시각**(UTC, 초 단위 절삭)이라 클라이언트 시계와 수 초 오차가 날 수 있습니다.
  90일 정확히를 노리지 말고 여유를 둘 것 — 권장은 180일 또는 무기한.
- **이미 발급된 키는 영향 없습니다.** 하한은 발급 시점에만 적용되고 인증 경로의 만료 판정은 그대로입니다.

**권장 운영값**

| 용도 | `expires_at` |
|---|---|
| 상시 가동 헤드리스 호스트 | **무기한(생략/0)** + `last_used_at` 모니터링 + 필요 시 즉시 폐기 |
| CI 러너 / 임시 워커 | 180일(분기 회전) |
| 감사 요건상 만료가 필수인 환경 | 90일(회전 주기를 캘린더에 고정) |

### C. 401 응답 계약 (필수 — 이미 클라이언트가 의존)

만료·폐기·무효 키는 반드시 **401 또는 403**을 반환해야 합니다. 클라이언트는 이 상태 코드로
"자격증명 사망"을 판정하고 프로세스를 종료합니다(재시도 대상인 5xx·타임아웃과 구분).

```
401 { "error": { "code": "invalid_token",  "message": "..." } }   # 또는 평면 {code,message}
401 { "error": { "code": "token_expired",  "message": "..." } }
```

`code` 값은 자유지만, 위 두 값 또는 `unauthorized`를 쓰면 클라이언트가 SSE 오류 이벤트에서도
인증 실패로 인식합니다(HTTP 상태만으로도 판정되므로 필수는 아님).

**5xx로 내려보내지 마세요** — 클라이언트가 일시 장애로 오인해 무한 재시도합니다.

### D. 관리 엔드포인트 (필수)

어드민 권한 기준. 경로·envelope는 기존 관리 API 관례를 따르면 됩니다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| `POST` | `/api/v1/service-accounts` | 생성 — `{ name, owner_member_id, description? }` → `{ id, name }` |
| `GET` | `/api/v1/service-accounts` | 목록(키 메타 포함, 평문 키 제외) |
| `DELETE` | `/api/v1/service-accounts/{id}` | 계정 폐기(딸린 키 전부 무효) |
| `POST` | `/api/v1/service-accounts/{id}/keys` | 키 발급 — `{ expires_at? }` → `{ key_id, token, expires_at }` ← **평문 `token`은 여기서만**. 90일 하한 위반 시 `400`([B-1](#b-1-키-수명-하한-90일--서버-강제-2026-07-27-반영-완료)) |
| `GET` | `/api/v1/service-accounts/{id}/keys` | 키 목록 — `{ key_id, created_at, expires_at, last_used_at, revoked }` |
| `DELETE` | `/api/v1/service-accounts/{id}/keys/{key_id}` | 키 폐기 |

`last_used_at`은 방치된 키를 찾는 데 필요합니다(운영 위생).

### E. 감사 로그 (권장)

에이전트 행위를 추적하려면 서비스 계정 id와 함께 **레지스트리 `agent_id`**가 로그에 남아야 합니다.
한 서비스 계정으로 여러 에이전트를 띄우는 구성이 일반적이라, 계정 id만으로는 어떤 인스턴스인지 모릅니다.

## 3. 클라이언트 영향

**없습니다.** API 키를 `Authorization: Bearer`로 받는 한, `OHMYAGENT_AUTH_TOKEN`에 JWT 대신 API 키를
넣기만 하면 동작합니다. 클라이언트 코드 변경이 필요한 설계(별도 헤더, 서명 기반 인증 등)는 피해 주세요.

90일 하한(B-1)도 런타임 영향은 없습니다 — 발급은 관리 API 1개에서만 일어나고, 이 저장소에는 그 엔드포인트를
호출하는 코드가 없습니다(GUI·헤드리스 모두 토큰을 주입받기만 함). 다만 **나중에 키 발급 UI나 스크립트를
붙일 때는** 만료일 입력에 클라이언트 측 하한(오늘 + 90일)을 걸어 서버 왕복 전에 막고, 400 메시지는
"만료일은 최소 90일 이후여야 합니다"로 번역해 노출해야 합니다.

## 4. 부록 — 헤드리스/GUI 구분 (별건, 우선순위 Low)

현재 클라이언트는 모든 요청 `metadata.os`에 `"windows"`를 **하드코딩**해 보냅니다. 리눅스 헤드리스도
`windows`로 보고돼, 서버가 "헤드리스는 도구를 더 조인다" 같은 정책을 세울 근거가 없습니다.

이걸 풀려면 양쪽이 함께 바뀌어야 합니다:

- **클라이언트**: 실제 OS와 실행 형태(`gui` / `headless`)를 metadata에 실음
- **서버**: 도구 정책을 실행 형태별로 분기 가능하게

서비스 계정(§2)이 도입되면 **계정 분리만으로 대부분의 통제가 가능**하므로 우선순위는 낮습니다.
계정을 나누기 어려운 구성이 생기면 그때 논의하면 됩니다.

## 5. 도입 전까지의 운영

서비스 계정이 나오기 전에는 다음으로 버팁니다(자세히는 `headless-deployment.md`):

1. 에이전트 전용 **사람 계정**을 만들어 그 계정의 JWT를 주입 — 최소한 권한·감사는 분리됩니다
2. 토큰 만료 시 클라이언트가 **종료 코드 77**로 죽고 systemd가 재시작 — 좀비 상태는 발생하지 않습니다
3. 만료 주기에 맞춰 토큰을 갱신하는 운영 절차를 둡니다

이 방식의 한계는 명확합니다 — **만료 시점에 사람이 개입해야 합니다.** 그래서 §2가 필요합니다.
